# SearXNG и OpenRouter: контракт обогащения данных

Проверено по официальной документации 14 сентября 2026 года. Это контракт для реализации и проверки соединений, а не отчёт об уже выполненных запросах. Версию SearXNG, доступные движки, модели и фактические расходы конкретного запуска нужно записать после проверки среды пользователя. Документация SearXNG на дату проверки имеет версию `2026.9.14+ef05645f0`; сервер пользователя может работать на другой версии.

Пайплайн последовательно ищет источники через существующий SearXNG, получает текст выбранных публичных документов и передаёт OpenRouter ограниченный пакет свидетельств для извлечения полей. Модель предлагает записи; валидатор принимает только подтверждённые значения. Расходы на модели разрешены пользователем. Объём каждого прогона задаётся исследовательским вопросом и фиксированной выборкой, а учёт расходов охватывает все попытки, включая неудачные.

## SearXNG: обнаружение возможностей

Сначала выполнить `GET /config`. В журнал разрешено переносить только необходимые поля: `version`, список категорий и для движков `name`, `enabled`, `categories`, `paging`, `language_support`, `languages`, `time_range_support`, `safesearch`, `timeout`, если они присутствуют. Старые версии могут возвращать меньше полей. Это сведения о конфигурации, а не доказательство того, что каждый движок сейчас отвечает. Список названий получают от конкретного сервера: заранее считать Google, Bing или любой другой движок доступным нельзя. [Administration API](https://docs.searxng.org/admin/api.html), [реализация `/config`](https://github.com/searxng/searxng/blob/master/searx/webapp.py#L1133).

`GET /healthz` в текущем официальном коде возвращает `OK`. Он проверяет доступность приложения, но не работоспособность внешних поисковых сервисов. После него нужен один содержательный тестовый поиск с проверкой результатов и ошибок движков. Отсутствие `/healthz` или `/config` на конкретной версии записывается как недоступная проверка, а не автоматически как отказ поиска. [Реализация `/healthz`](https://github.com/searxng/searxng/blob/master/searx/webapp.py#L546).

Если требуется прочитать настройки по уже настроенному SSH, выводить только разрешённые поля после разбора конфигурации: например, наличие `json` в `search.formats`, `search.max_page`, имена и состояния движков. Не печатать `settings.yml`, `.env`, `docker inspect` или окружение целиком: они могут содержать ключи поисковых API, прокси и `server.secret_key`. Проверка соединения не изменяет настройки и не перезапускает сервис. `/config` сам по себе не доказывает, что JSON разрешён: это проверяется запросом поиска или разрешённым фрагментом фактической конфигурации.

## SearXNG: запрос и ответ

Официальный API поддерживает `GET /search` с query parameters и `POST /search` с формой `application/x-www-form-urlencoded`. Для Python HTTP-клиента POST передаёт словарь через `data=`, а не `json=`. Обязателен непустой `q`; нужен `format=json`. Если JSON не включён в `search.formats`, сервер возвращает 403. [Search API](https://docs.searxng.org/dev/search_api.html).

| Параметр | Контракт клиента |
|---|---|
| `q` | Явный запрос с названием МО, регионом и искомым свойством; идентификатор МО хранится отдельно |
| `format` | Всегда `json` |
| `pageno` | Целое число, начиная с 1 |
| `language` | Явно выбранный поддерживаемый язык, например `ru`; проверить фактические возможности движков |
| `engines` | Проверенные имена движков через запятую; передавать без `categories` при строгом выборе движков |
| `categories` | Например, `general`, только если сознательно используется выбор по категории вместо явного списка движков |
| `safesearch` | Явное значение 0, 1 или 2; поддержка зависит от движка |
| `time_range` | Не передавать для исторической проверки 2023–2024 годов; документированные `day`, `month`, `year` ограничивают относительный период и не задают историческую дату доступности |

Имена движков проверяются до отправки. В текущем `webadapter.py` неизвестные имена отбрасываются; при отсутствии корректного выбора могут использоваться настройки по умолчанию. Совместная передача `engines` и `categories` может расширить набор движков. Запросы с управляющими bangs не включаются в автоматические шаблоны: они могут менять выбор движка или вести к редиректу. Поле `week` поддерживается текущим парсером, но не перечислено на странице Search API; минимальный контракт на него не опирается. [Парсер параметров](https://github.com/searxng/searxng/blob/master/searx/webadapter.py).

Ответ проверяется как JSON-объект с массивом `results`. Полезные поля результата: `url`, `title`, `content`, `engine` или `engines`, при наличии — дата публикации. Дополнительные поля допустимы; отсутствующее необязательное поле не заполняется догадкой. В текущем сериализаторе верхний уровень включает `query`, `results`, `answers`, `corrections`, `infoboxes`, `suggestions`, `unresponsive_engines`. Поле `number_of_results` не является обязательным и в этой версии отсутствует. [Сериализатор ответа](https://github.com/searxng/searxng/blob/master/searx/webutils.py#L149).

Пагинация — последовательные `pageno=1,2,...` до заданного в конфигурации числа страниц. Учитываются `paging` движков и серверный `search.max_page`; значение 0 у последнего означает отсутствие серверного ограничения, но ограничения самого движка остаются. [Настройки поиска](https://docs.searxng.org/admin/settings/settings_search.html). Предлагаемое правило клиента: остановиться при пустой странице без ошибок либо когда страница не добавила новых допустимых URL. Результат с `unresponsive_engines` сохраняется как частичный. Пустая выдача при отказавших движках не доказывает отсутствие источников.

На каждую страницу сохраняются `search_request_id`, `territory_id`, запрос, параметры, время UTC, HTTP-статус, длительность, число результатов, хеш ответа и безопасная сводка ошибок движков. URL нормализуются для удаления повторов с сохранением исходного адреса. Сниппет используется для выбора страницы, а не для окончательного подтверждения факта. Оператор `site:` также проверяется по фактическому домену результата: его поддержка зависит от поискового сервиса. [Search API](https://docs.searxng.org/dev/search_api.html).

## OpenRouter: модель, запрос, структура

Используется `POST https://openrouter.ai/api/v1/chat/completions` с JSON-телом и заголовком `Authorization: Bearer …`. Python-клиент передаёт тело через `json=`. Ключ берётся из настроенного секретного источника в память процесса; он не входит в конфигурацию исследования, командную строку, URL, промпт или журнал. Необязательные заголовки атрибуции приложению для этого пайплайна не нужны. [Quickstart](https://openrouter.ai/docs/quickstart).

Перед запуском получить каталог `GET /api/v1/models` и сохранить для выбранных моделей `id`, `canonical_slug`, `context_length`, `supported_parameters`, `pricing` и доступные ограничения `top_provider`. Каталог меняется; модель выбирается по пригодности к задаче, а не по заранее запомненному имени или минимальной цене. При использовании пагинации каталог поддерживает `offset` и `limit`; если оба опущены, документация обещает полный список. [Models API](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties).

Проверить выбранный маршрут через `GET /api/v1/models/{author}/{slug}/endpoints`: у конкретного endpoint доступны `context_length`, `max_prompt_tokens`, `max_completion_tokens`, `supported_parameters`, цена и сведения о провайдере. Отсутствующее ограничение не считать бесконечностью. Длина входа, служебные сообщения, схема и резерв ответа должны помещаться в контекст выбранного endpoint. [Endpoints API](https://openrouter.ai/docs/api/api-reference/endpoints/list-all-endpoints-for-a-model).

В запросе фиксируются следующие значения; имена в угловых скобках — параметры реализации, а не строки для отправки:

```text
model: <проверенный model id>
messages: <инструкция извлечения и пакет документов с source_id>
stream: false
max_tokens: <достаточный предел ответа в пределах endpoint>
provider.require_parameters: true
response_format.type: json_schema
response_format.json_schema.name: municipal_evidence
response_format.json_schema.strict: true
response_format.json_schema.schema: <версионированная JSON Schema>
```

Поддержка structured outputs определяется endpoint, а не только названием модели. `strict=true` не отменяет локальную валидацию: способы соблюдения схемы у провайдеров различаются. В схеме нужны явные типы, обязательные поля и `additionalProperties=false`; неизвестное значение допускается как `null`. Режим `json_object` обеспечивает более слабый контракт и не заменяет проверку схемы. [Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs).

`provider.require_parameters=true` исключает маршруты, не поддерживающие переданные параметры. Для воспроизводимого сравнения фиксируются конкретные модель и политика провайдеров. Если разрешены fallback-провайдеры, они остаются в заранее выбранном наборе; фактический провайдер записывается в журнал. Переход на другую модель — отдельное, видимое условие эксперимента. Параметр `temperature` добавляется только при подтверждённой поддержке; нулевая температура не гарантирует одинаковые ответы. [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection).

Для первого варианта выбран `stream=false`: проще целиком проверить JSON, ошибки, завершение и usage. Успех требует содержимого `choices[0].message.content`, допустимого `finish_reason`, отсутствия ошибки и отказа модели, корректной схемы и пройденной проверки свидетельств. Ответ, оборванный по лимиту, не принимается частично и не дополняется предположениями.

Если позже нужен streaming, следует использовать полноценный SSE-парсер: учитывать комментарии, многострочные события, `[DONE]`, ошибки внутри потока и отдельный финальный кадр usage. Частичный JSON не публикуется как результат. `X-Generation-Id` можно сохранить после получения заголовков; потеря последнего кадра usage требует сверки по этому идентификатору. [Streaming](https://openrouter.ai/docs/api_reference/streaming).

## Ошибки, повторы и расходы

У обоих клиентов должны быть отдельные тайм-ауты соединения и чтения, общий срок выполнения задания, ограничение числа попыток и размера ответа. Значения сохраняются в конфигурации. В качестве начального инженерного правила предлагаются не более 3 попыток на операцию и небольшой управляемый параллелизм; это не лимит разрешённых пользователем расходов. Между временными сбоями применяется экспоненциальная задержка со случайным разбросом. Если `Retry-After` превышает оставшееся время задания, запрос откладывается, а не повторяется раньше указанного срока.

| Ситуация | Действие |
|---|---|
| SearXNG 400 | Исправить параметры; такой же запрос не повторять |
| SearXNG 403 или HTML вместо JSON | Зафиксировать ошибку доступа/формата; проверить JSON и прокси, не считать выдачу пустой |
| SearXNG 429, временный 5xx, сетевой сбой | Ограниченный повтор; уважать подсказку сервера о задержке |
| OpenRouter 400, 401, 402, 403 | Остановить этот запрос; исправить параметры, доступ или состояние кредита. Автоматических покупок и смены ключа нет |
| OpenRouter 429, 502, 503 или другая подтверждённая временная ошибка | Ограниченный повтор с учётом `Retry-After` и разрешённого маршрута |
| HTTP 200 с `error`, ошибкой в `choices` или `finish_reason=error` | Считать неудачной генерацией; сохранить доступный usage и безопасный код ошибки |
| Нет содержимого, нарушена схема, отказ модели | Не принимать поля; записать причину. Исправленный запрос считается новой попыткой |

OpenRouter может передать ошибку после начала генерации внутри тела ответа; одного HTTP-статуса недостаточно. По возможности использовать `error.metadata.error_type`, не выводя необработанные `metadata` и сообщения провайдера: они могут содержать фрагменты входных данных. Даже ответ без содержимого иногда оплачивается. [Errors and Debugging](https://openrouter.ai/docs/api_reference/errors-and-debugging).

Перед запуском можно прочитать `GET /api/v1/key`, оставив в служебной сводке только нужные числовые ограничения и потребление. `limit_remaining=null` означает отсутствие лимита этого ключа, а не доказательство бесконечного баланса аккаунта. Не предполагать универсальный RPM для платных моделей и не требовать `X-RateLimit-*` у успешных ответов: ограничения могут исходить от OpenRouter или провайдера. [Limits](https://openrouter.ai/docs/api_reference/limits).

Текущая документация сообщает, что usage включается автоматически. Параметры `usage: {include: true}` и `stream_options: {include_usage: true}` устарели. Сохраняются `prompt_tokens`, `completion_tokens`, `total_tokens`, доступные сведения о reasoning/cache и `usage.cost`. Последнее — списанная с аккаунта сумма в кредитах; `cost_details.upstream_inference_cost` имеет другой смысл и не прибавляется к ней. [Usage Accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting).

Резервная сверка — `GET /api/v1/generation?id=<generation_id>` с тем же способом авторизации. Из ответа нужны фактические `model`, `provider_name`, `total_cost`, данные токенов, время и причина завершения. Это сверка той же генерации: суммы из ответа completion и generation нельзя складывать. [Generation API](https://openrouter.ai/docs/api/api-reference/generations/get-request-&-usage-metadata-for-a-generation).

После read timeout сервер мог уже обработать и оплатить запрос. Контракт не предполагает идемпотентности повторного POST. При известном `generation_id` сначала уточняется статус и стоимость; без него попытка остаётся с неизвестным исходом. В отчёте показываются подтверждённая сумма и число попыток с неизвестной стоимостью. `null` не заменяется на 0. Цена из каталога служит оценкой до запроса; фактический счёт строится по usage. Денежные значения суммируются десятичной арифметикой.

## Приём только подтверждённых полей

Это правила проекта, а не обещания API. Каждый документ получает `source_id`, исходный и конечный URL, заголовок, издателя, время получения UTC, статус загрузки и хеш использованного текста. Дата публикации, дата события и период действия свойства хранятся отдельно; неизвестные даты остаются пустыми. В модель передаются текст и эти метаданные, а не только адрес страницы. Текущий документ не доказывает, что информация была доступна в 2023 или 2024 году.

Минимальная предлагаемая запись извлечения:

| Поле | Требование |
|---|---|
| `territory_id`, `field` | Код из входного списка и разрешённое имя свойства |
| `value`, `unit` | Типизированное значение; единица обязательна там, где она нужна по смыслу |
| `valid_from`, `valid_to`, `date_precision` | Датировка свойства, без выдуманного дня при известном только годе |
| `status` | `supported`, `conflict` или `unknown` |
| `evidence` | Список `source_id`, коротких цитат и указателей на место в сохранённом тексте |
| `reason` | Краткое объяснение неопределённости или конфликта; оно само по себе не является доказательством |

Валидация идёт после JSON Schema. Код МО должен совпадать с входом, имя свойства — с разрешённым списком, `source_id` — с переданным пакетом. Цитата сверяется с сохранённым текстом; допустима только заранее заданная нормализация пробелов. Затем проверяются принадлежность источника нужному МО и региону, смысл единицы, даты, границы и административный уровень. Одинаковое название другого муниципалитета не подтверждает поле. Наличие цитаты без смысловой поддержки утверждения также недостаточно.

`supported` принимается только при прямом подтверждении свойства. Для `unknown` значение остаётся `null`; противоречащие источники сохраняются как `conflict` с обеими ссылками. Сниппеты, автоматические ответы поисковика, знания модели и согласие второй модели не заменяют первичный документ. Интерпретации вроде «туристический профиль» отделяются от извлечённых фактов и остаются гипотезами экономического трека. Отсутствие найденной информации не доказывает отсутствие свойства.

Тексты страниц обрабатываются как недоверенные данные. Их команды не меняют инструкцию извлечения, модель, список полей, лимиты или адреса сервисов. Загрузчик публичных источников принимает только HTTP(S), проверяет редиректы и блокирует локальные/служебные адреса; разрешённый частный SearXNG настраивается отдельно и не становится доступным через URL из выдачи. Заголовок OpenRouter Authorization никогда не пересылается источникам или SearXNG. Не следует исполнять код со страниц или включать в модель конфигурацию сервера.

## Журнал и проверка готовности

Предлагаемый отдельный каталог обогащения содержит манифест, журнал поисков, каталог источников, записи извлечений и журнал попыток модели. Его фактический путь задаёт реализация; эти имена пока не объявляются уже существующими артефактами. На попытку модели записываются `run_id`, `task_id`, `attempt`, время, хеши промпта/схемы/пакета источников, запрошенная и фактическая модель, провайдер, `generation_id`, HTTP-статус, безопасный класс ошибки, `finish_reason`, длительность, usage и результат валидации. Повтор не перезаписывает предыдущую попытку. Секреты, полные заголовки и необработанные отладочные ответы не логируются.

Перед содержательным прогоном проверяются один реальный поиск, один извлечённый факт с точной ссылкой и один случай, где правильный результат — `unknown`. Отдельные проверки клиента должны покрыть частичную выдачу, 429, HTML вместо JSON, оборванную генерацию, чужой `territory_id`, выдуманную ссылку и отсутствие usage. Далее запускается заранее описанный блок МО и свойств. В отчёте нужны число рассмотренных и принятых полей, доли `unknown`/`conflict`, причины отказов, фактические токены и стоимость. Новые запросы выполняются для закрытия названных пробелов, а не ради увеличения числа вызовов.

## Реализованный низкоуровневый клиент

Классы находятся в `enrichment/src/sber_enrichment/clients.py`, независимо от замороженного количественного пайплайна. `SearxClient.config()` и `search(...)` возвращают JSON сервера; `OpenRouterClient.models()` возвращает каталог, а `complete_json(...)` — `parsed`, `response_id`, `usage`, `model`, `finish_reason`. Клиенты поддерживают `with` и `close()`. `ClientError` содержит безопасный код и доступные `status`, `response_id`, `usage`; исходные ошибки транспорта и провайдера не включаются в текст исключения. В `client.attempts` сохраняется метаинформация каждой внутренней попытки; при параллельных вызовах каждый ответ обновляет собственную запись.

Аргумент `OpenRouterClient(attempt_log_path=...)` включает журнал на диске. Клиент загружает прежние записи и атомарно сохраняет полный JSON после начала попытки, заголовков, получения тела и usage, ошибки, решения о повторе и окончательной валидации. Запись защищена `threading.Lock`, файл и каталог синхронизируются с диском там, где это поддерживается. Один путь обслуживает один экземпляр клиента; блокировка не предназначена для нескольких процессов. `call_id` связывает повторы, `attempt_id` различает попытки, а `method` и `operation` позволяют отделить бесплатный `GET /api/v1/models` от генераций. Незавершённая запись с неизвестным usage сохраняет неопределённость после перезапуска. Оркестратор не очищает список, не дописывает прежние записи повторно и не считает этот журнал вместе с дублирующими итогами вызовов.

Ключ читается из явно переданного файла, затем из `OPENROUTER_API_KEY_FILE`, иначе из `OPENROUTER_API_KEY`. Клиент не копирует его в проект. У OpenRouter фиксирован адрес API; редиректы отключены. Повторяются только HTTP 429 и 5xx, максимум 3 попытки по умолчанию. Тайм-ауты и ошибки транспорта не повторяются автоматически. Если `Retry-After` больше 60 секунд, возвращается `retry_deferred`: планировщик может продолжить позже, не нарушая указанный сервером срок. Идентификатор генерации из заголовков сохраняется даже при последующем обрыве чтения.

`PublicFetcher.fetch()` возвращает `url`, `final_url`, `status`, `content_type`, `body` в байтах, `sha256`, `error`. Он принимает публичные HTTP(S)-адреса с портами 80/443, отклоняет userinfo и IP-литералы во входе, проверяет все DNS-адреса и каждый редирект. Соединение закрепляется за проверенным IP; исходное имя используется в Host и TLS SNI. Прокси из окружения и автоматические редиректы отключены. Механизм SNI предусмотрен публичным [контрактом HTTPX](https://www.python-httpx.org/advanced/extensions/#sni_hostname); типы тайм-аутов описаны в [документации HTTPX](https://www.python-httpx.org/advanced/timeouts/).

Загрузчик запрашивает `Accept-Encoding: identity`; для сайтов, игнорирующих этот запрос, следующая версия также принимает `gzip`. Составные цепочки `Content-Encoding` и другие кодировки отклоняются, кроме узкого случая ошибочного заголовка PDF, описанного ниже. Автоматическая распаковка HTTPX не используется: `iter_raw()` отдаёт скачанные байты, а `zlib.decompressobj()` распаковывает gzip с ограничением `max_length` на каждый вызов. Проверяются CRC, конец каждого member и отсутствие неполного или постороннего хвоста; корректные последовательные members объединяются с общими лимитами. Принцип работы `max_length`, `eof` и `unused_data` описан в [документации Python 3.12](https://docs.python.org/3.12/library/zlib.html).

Только для точных хостов `www.sberbank.ru` и `sber.ru` допускается ответ с объявленным `Content-Encoding: aws-chunked`, если полное прочитанное тело начинается с `%PDF-`. Для этих источников обнаружен ошибочный заголовок при фактической передаче обычного PDF. Тело читается с обоими прежними лимитами и не преобразуется. Настоящее chunk framing, иной префикс и переход на другой хост не принимаются как этот случай. У принятого ответа сохраняются `declared_content_encoding="aws-chunked"` и `encoding_note="declared_aws_chunked_but_received_bare_pdf"`; SHA256 относится к неизменённым байтам PDF. Эта проверка префикса разрешает передачу документа парсеру, но не заменяет проверку его содержимого.

`max_bytes` ограничивает распакованный документ; `max_compressed_bytes` отдельно ограничивает скачанные байты и по умолчанию равен `max_bytes`. До чтения проверяется доступный `Content-Length`, затем оба ограничения проверяются по фактическому потоку. По умолчанию допускаются 8 000 000 байт каждого вида, 30 секунд и 5 редиректов; параметры конструктора позволяют задать другой объём. SHA256 относится к распакованному `body`. Системное разрешение DNS использует тайм-аут ОС; после него оставшееся время проверяется повторно. Ошибка TLS не приводит к отключению проверки сертификата. При ошибке или превышении размера частичный документ не возвращается как успешный источник.

Локальная JSON Schema проверяется до вызова модели, внешние `$ref` запрещены, результат проверяется после разбора. Используется явный реестр без сетевой загрузки схем; неизвестный URI не запускает дополнительный HTTP-запрос. [Валидация jsonschema](https://python-jsonschema.readthedocs.io/en/stable/validate/). Смысл цитат, принадлежность МО и решение о принятии поля проверяет следующий слой пайплайна: структурная валидация клиента этого не доказывает.

Проверки клиентов используют `httpx.MockTransport` и локальные подмены DNS; реальные платные вызовы и сервер пользователя этими тестами не затрагиваются. [Транспорт для тестов HTTPX](https://www.python-httpx.org/advanced/transports/#mock-transports).

## Дополнительные цепочки TLS для отдельных источников

Диагностика на сервере 2026-09-14 выявила разные причины ошибок. `sberindex.ru` отдавал только сертификат сайта без промежуточного `LiteSSL RSA CA 2025`. Этот промежуточный сертификат из AIA проверен через уже доверенный корень системного хранилища и certifi; добавлять новый корень для SberIndex не потребовалось. После восстановления цепочки сервер вернул HTTP 403. Это ограничение HTTP остаётся зафиксированной ошибкой доступа.

`rosstat.gov.ru` использовал `Russian Trusted Sub CA`, выпущенный 15.07.2024 и действующий до 19.07.2029. Промежуточный сертификат 2022 года из старой инструкции не замыкает эту цепочку. Корень и обе версии промежуточного сертификата уже находились в доверенном хранилище Windows пользователя; экспортированы только их публичные сертификаты. Подпись версии 2024 года дополнительно проверена официальным корнем. Первичные ссылки: [инструкция Сбера](https://developers.sber.ru/help/certificates/how-to), [официальный корень](https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt), [промежуточный сертификат из AIA](http://nuc-cdp.digital.gov.ru/cdp/subca_ssl_rsa2024.crt). Получение промежуточного сертификата по HTTP само по себе не устанавливает доверие: его цепочка проверяется до использования.

`PublicFetcher(ca_bundles={hostname: pem_path})` добавляет сертификаты к базовому certifi только для точного имени хоста. Проверка имени и цепочки остаётся обязательной; режим доверия произвольному промежуточному сертификату отключён. Каждый редирект заново выбирает контекст, поэтому дополнительное доверие не распространяется на поддомены или соседние сайты. OpenRouter, SearXNG, глобальное хранилище ОС и другие сервисы не меняются. Путь `PUBLIC_CA_BUNDLES_JSON` указывает на JSON-словарь имён и абсолютных путей PEM; оркестратор читает его и передаёт аргумент `ca_bundles`. Сам низкоуровневый загрузчик не читает этот env-параметр.

На сервере файлы размещены в `/home/vpnadmin/services/sberindex-enrichment/certs/`: `ca-bundles.json`, `certificate-sources.json`, `russian-trusted.pem`, `litessl-intermediate.pem`. В журнале происхождения записаны источники и SHA256. Повторная проверка PublicFetcher получила HTTP 200 для MUNST (24 934 байта) и `bdmo_met2024.docx` (162 482 байта); SearXNG `google cse` вернул 20 результатов без недоступных движков. PDF метаданных муниципальных границ Сбера прошёл TLS и вернул HTTP 200, но первоначальная серверная версия отклонила его из-за `Content-Encoding`, отличного от запрошенного `identity`. Это не считается успешно загруженным документом.

Прогон `research-20260914-01` стартовал с первоначальной серверной версией без gzip. Во время его выполнения серверный код не заменялся. Следующая локальная версия с ограниченной распаковкой проверяется отдельно; последующий проход только по источникам может обновить тела документов без вызовов OpenRouter. Для такого прохода нужны отдельный манифест и хеш версии клиента. Изменившийся пакет свидетельств не должен незаметно подменять вход уже выполненного анализа модели.
